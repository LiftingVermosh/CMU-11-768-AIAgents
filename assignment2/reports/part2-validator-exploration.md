# Part 2：验证器设计与迭代记录

记录 `validator/solution.py` 的设计推导、四轮迭代的实测数据、以及两个在调参过程中才暴露出来的机制性问题。
所有分数均在公开 seed 集上、用 `workflow score` 计算；所有"我们发现"的结论都标注了对应的 run_id 以便复核。

---

## 0. 环境偏差（须在报告中声明）

| 项 | 课程默认 | 本项目实际 | 影响 |
| --- | --- | --- | --- |
| 模型部署 | Modal 上的 vLLM | OpenRouter 按量付费 | 验证器模型为 `qwen/qwen3-vl-30b-a3b-instruct`（对应课程的 `Qwen/Qwen3-VL-30B-A3B-Instruct-FP8`）；三个生成智能体之一替换为 `qwen/qwen3-coder-30b-a3b-instruct` |
| Harbor 网络策略 | `network_mode = "no-network"` | `"public"` | WSL2 内核缺 `CONFIG_NFT_FIB_INET`，Harbor 的 Docker provider 用它实现断网侧车，因此会拒绝任何声明 `no-network` 的任务。任务运行时不访问网络，奖励不变，仅损失隔离性保证 |

`validator/model.py` 的 `tokenize` / `detokenize` 是 vLLM 专有路由，在 OpenRouter 上返回 404，因此本实现**不依赖**基线那套上下文压缩逻辑，改为按字符数截断。

## 1. 基线诊断（Part 1）

### 1.1 全量 110 run 的基线成绩

```
execution_failure  MCC=+0.0524  TP=5  TN=65 FP=33 FN=7
wrong_data         MCC=-0.0293  TP=1  TN=69 FP=4  FN=24
wrong_chart        MCC=+0.1430  TP=5  TN=27 FP=0  FN=66
hard_to_read       MCC= 0.0000  TP=0  TN=59 FP=0  FN=39
macro_mcc          0.0415
```

一个更直观的概括：基线对 **59 个 run 判为"无错误"，其中只有 2 个真的无错误**。它实际上在预测"没问题"这个近似常量，这正是 MCC 给出接近 0 的原因。

### 1.2 三个失效模式

**失效 A：`execution_failure` 假阳性（33 个）**

run `004, 022, 031, 034, 046, 055, 062, 070, 074, 075, 079, 082, 091, 097, 104, 105, 108, 111, 124, 125, 141, 150, 153, 155, 156, 163, 165, 167, 175, 199, 203, 204, 216`。

证据是模型的自相矛盾：`evidence` 字段写着 "The agent did not crash, exhaust its turns, or give up; it produced a valid figure"，而回答仍以 `YES` 开头（`baseline.py:159` 的解析据此判定为错误）。这不是模型看错了图，是 VLM 的 yes/no 头不可靠。

**失效 B：`wrong_chart` 与 `hard_to_read` 假阴性**

`wrong_chart` 漏 66/71、`hard_to_read` 漏 39/39。基线的问法是"这张图有没有违反指令的任何部分"和"这张图是否难以阅读"，都是**开放式整体判断**。模型退化成"整体看着还行"，默认答 NO。

**失效 C：类别划分的模糊**

`004` 同时被标 `wrong_data`（第四个面板漏了立方步骤）和 `wrong_chart`（第三个子图的 x 轴应为 log）。同一个 run 上两类错误并存，说明"错在哪一类"取决于**证据的来源**，而不是错误的严重程度。

### 1.3 由此确立的三条设计原则

1. **能从产物确定性推出的判据，绝不问模型。**
2. **不要在单次调用里塞多个检查项** —— 先抽取显式清单，再逐条核对，并要求引用证据。
3. **把"判断"改写成"查找"** —— 要求模型引用指令原文与图中所见，可以显著降低幻觉。

## 2. 类别边界的实证定义

`seed_labels.json` 的 `evidence` 是助教按评分标准手写的，直接给出了各类的操作性定义：

| 类别 | 证据来源 | 实测判定规则 |
| --- | --- | --- |
| `wrong_data` | 图所记录的**数值** | 该出现的系列/类别缺失、不该出现的没被过滤、数值算错（漏了变换）、数据未被映射到视觉量 |
| `wrong_chart` | 图所记录的**结构** | 图表类型、子图布局、轴的刻度类型与范围、刻度标签与轴标题、配色方案、图例有无、标记形状、线型、标签旋转、输出尺寸 |
| `hard_to_read` | 渲染出的**像素** | 前景与背景同色、文字互相重叠、被画布边缘裁切、字号过小 |

两条最容易混淆的边界，由同 run 多标签的样本划定：

| 情形 | 归属 | 例证 |
| --- | --- | --- |
| 要求的配色方案被违反（禁用 rainbow 却用了） | `wrong_chart` | `013` |
| 配色**导致看不见**（前景 = 背景色） | `hard_to_read` | `030` `038` `052` |
| 数据**没有画** | `wrong_data` | `008` |
| 数据画了但**看不见** | `hard_to_read` | `030` |
| 数据**未映射到视觉量**（各扇形半径相同） | `wrong_data` | `025` |
| 视觉编码**规格不对**（全灰 + 空图例） | `wrong_chart` | `025` |

`hard_to_read` 的判据**完全不依赖 instructions** —— 这一点直接决定了它的实现方式（prompt 里不带指令，省 token 也更聚焦）。

## 3. 验证器结构

```
validate(run)
├── judge_execution            纯代码判定，0 次模型调用
│     无 figure / 无法解码 → [execution_failure]（单独出现，短路）
└── judge_data_and_chart       3 次调用
│     ├── _requirements        抽取：instructions → 编号清单，每条自带 family 分类
│     ├── _audit(WRONG_DATA)   核对：清单 + 图 + agent 的代码
│     └── _audit(WRONG_CHART)  同上，只带 chart 类条目
└── judge_readability          1 次调用，只给图 + 画布尺寸，不给 instructions
```

**4 次调用 / run，与基线持平** —— EF 那一次省下来的调用正好付了"抽取"这一步。

### 3.1 `judge_execution`：确定性判据

`run.figure is None` 或 PIL 无法解码（`verify()` 抛异常）即判 `execution_failure`。

seed 集上验证过：**12 个 `execution_failure` 真值恰好等于"没有 figure.png"，且反过来 12 个没有图的 run 全是 EF**，完全等价。

注意 `Image.verify()` **返回 `None` 而不是布尔值**，成功时抛异常才算失败。写成 `not Image.open(p).verify()` 会把每一张完好的图都判成 EF。

### 3.2 拆解式审计

**为什么要把 agent 的代码送进数据审计**：像"第四个面板漏了立方步骤"这类错误，**看像素是判不出来的** —— 没人能从对数轴读出 `15 ** x` 还是 `x ** 3`，而指令只说了"cubed data"。代码里一眼可见。实现上从 `tool_calls[].function.arguments` 抽取，只保留含 `.py` / `EOF` / `<<` 的文件写入命令，实测 run `004` 抽出 1900 字符（整条轨迹 JSON 是 16 KB）。

**解析器锚定行首**：判定必须紧跟编号（`^<n>. <VERDICT>`），因此 "4. The axis looks linear which is OK" 这类行会被**跳过**而不是误读成一条 OK。误读产生错标签，跳过只损失召回。

### 3.3 可读性：从"判断"改为"找缺陷"

不问"这张图难读吗"，而是列五个具体可观察的缺陷让模型去找，并要求给出引用的文字/元素与位置。

**图必须原尺寸发送** —— 缩图会制造出正在被检查的那个缺陷本身。

### 3.4 契约与容错

| 约束 | 强制者 | 违反后果 |
| --- | --- | --- |
| `evidence` 非空 | `Field(min_length=1)` | 契约错误，**整个 sweep 立即终止** |
| 每类每 run 至多一条 | `workflow/evaluate.py:112` | `score` 阶段报错 |
| `execution_failure` 单独出现 | 无代码强制 | 不报错，但须自行遵守 |

`validate()` **内部抛异常会被重试**，而**返回不合规对象会立刻终止整个 sweep** —— 因为构造 `Prediction` 的那一行在 `runner.py` 的 `try` 之外。因此解析失败时一律返回 `[]`（损失一个假阴性），绝不返回半成品。

## 4. 迭代记录

迭代一律在**子集**上进行（全量 110 run 一次约 $2–4、20–60 分钟）。

### 4.1 迭代 1：初版实现

**子集 v1（24 run）**，对照基线（同一子集）：

| family | 基线 | 迭代 1 |
| --- | --- | --- |
| execution_failure | +0.2750 | **+1.0000** |
| wrong_data | -0.2548 | +0.1690 |
| wrong_chart | 不可测 | 不可测 |
| hard_to_read | 0.0000 | +0.6831 |
| **macro** | **0.0050** | **0.4630** |

三个改法全部生效。`wrong_chart` 的 `MCC=0` 是**子集缺陷**：24 个 run 里 12 个非 EF run 全部带 `wrong_chart` 标签，负例为 0，分母含 `(TN+FP)=0`，MCC 按约定记 0。真正有信息量的是 `FN=5`。

**子集设计教训**：选子集时必须保证每个 family 都有正例和负例，否则 MCC 不可测。

### 4.2 迭代 2：三处 prompt 修复

| 修复 | 目标 | 依据 |
| --- | --- | --- |
| 抽取 prompt 加入颜色归属规则 | 颜色要求被误标为 `wrong_data` | run `052` 的"必须是绿色"被标成数据错误，真值算 chart |
| 数据审计加入前置条件 | 模型在指令未指定处自造违规 | run `030` 的指令未定义 `z`/`w`，模型却断言用了 meshgrid |
| 可读性检查项 1/5 收紧 | 对比度/字号的假阳性 | run `016` `028` |

在**相同的 24 个 run** 上隔离出 prompt 的净效果：

| family | 迭代 1 | 迭代 2 | 变化 |
| --- | --- | --- | --- |
| wrong_data | +0.1690 | +0.3714 | **+0.20** ✓ |
| hard_to_read | +0.6831 | +0.3714 | **-0.31** ✗ |
| macro | 0.4630 | 0.4357 | -0.03 |

数据侧的两处修复都生效（run `016` 的"过滤未应用"被抓住）。**可读性的收紧用 3 个真阳性换掉了 1 个假阳性**，明显亏本。

### 4.3 受控 A/B：确认收紧有害，且发现抖动

对 12 个 run 用三个变体各调两次（`/tmp/ab_readability.py`）：

| 变体 | 报出缺陷的 run 数 | 两次一致 |
| --- | --- | --- |
| `OLD`（原始措辞） | 9/12 | 11/12 |
| `NEW`（收紧 1/5 + "Density" 段） | 5/12 | 10/12 |
| `C`（2–5 保持原样，只改检查项 1） | 6/12 | 10/12 |

**关键发现：`NEW` 不是"精准收紧 1/5"，而是全局压制。** 真值落在检查项 3（裁切）和 4（背景色系列）的 run `030` / `038` / `046` 在 `OLD` 下各自报出 20 / 9 / 18 条缺陷，在 `NEW` 下全部变成 0。被修改的两项与它们无关，说明"Density alone is not illegibility"那句被模型读成了通用的"少报点"先验。

**结论：回退到 `OLD`。** 抽象措辞做不了精准修复。

### 4.4 抽取诊断：推翻了"抽取是瓶颈"的假设

对 5 个假阴性 run 单独调用抽取阶段（纯文本，不附图）：

| run | 真值要求 | 抽取到了吗 | 审计判了吗 |
| --- | --- | --- | --- |
| `021` | `wrong_chart`：缺 xlabel | ✅ "The x axis must be labeled" | ❌ 判 OK |
| `023` | 圆形标记 + 2x1 布局 | ✅ 两条都在 | ❌ 都判 OK |
| `016` | 过滤 <0.5% / 缺图例 | ✅ 两条都在 | 数据侧已修 / 图例 ❌ |
| `028` | 蓝线连 2015 / 缺图例 | ✅ 两条都在 | ❌ 都判 OK |
| `052` | 绿色竖线 | ✅ 已正确标为 `wrong_chart` | — |

**抽取阶段是健康的** —— 每一个被漏掉的要求都在清单里。瓶颈在**审计阶段把明显违规的要求判成 OK**，而且漏检有统一形状：**全部是"要求某物存在"**（图例、圆形标记、x 轴标签）。审计对"存在性"要求不去寻找，直接假设存在。

### 4.5 迭代 3：回退 + 存在性规则

| 改动 | 依据 |
| --- | --- |
| 可读性回退到 `OLD` 原文 | 4.3 |
| 两个审计 prompt 加入"存在性检查"规则 | 4.4：凡"必须存在"的要求，先在图里找到那个东西，指不出来即判 VIOLATED |
| 抽取补充几何/标记规则 | `052` `023`：几何与标记要求因"提到数据点"而被误标为 `wrong_data` |

**子集 v2（32 run）** 的结果，附基线对照：

| family | 基线 | 迭代 2 | 迭代 3 |
| --- | --- | --- | --- |
| execution_failure | +0.1189 | +1.0000 | **+1.0000** |
| wrong_data | -0.0335 | +0.1919 | +0.1919 |
| wrong_chart | 0.0000 | +0.4583 (TP7 FP1 FN5) | **+0.5334 (TP8 FP1 FN4)** |
| hard_to_read | 0.0000 | +0.4062 (TP4 FP1 FN5) | +0.3282 (TP7 FP5 FN2) |
| **macro** | **0.0214** | **0.5141** | **0.5134** |

存在性规则让 `wrong_chart` 的 `FN` 从 5 降到 4。可读性回退恢复了召回（`TP` 4→7）但暴露出 5 个假阳性。

### 4.6 迭代 4：定向修复（**已实现，尚未测量**）

迭代 3 暴露的 5 个 `hard_to_read` 假阳性**全部**是模型把常规图表文字判成"太小"或"对比度太低"：

```
[004]  1 -- "Exponential Decay (Decay Factor = 7.0)" -- top-left plot title
[022]  5 -- "0" -- bottom left, x-axis label        ← 刻度数字
[077]  5 -- "Water Storage (TAF)" -- y-axis label, too small to read clearly
[104]  5 -- "Number of Visits" -- on the left side, vertical axis label
```

`022` 和 `104` 是**真值完全无错**的 run。这是可预测的机械性幻觉，因此迭代 4 改为**直接点名那些被误判的物件**：

| 改动 | 目标 |
| --- | --- |
| 可读性 1/5 明确声明"常规深色轴标签/刻度数字/标题/图例在白底上可读，不是缺陷" | 5 个假阳性 |
| 数据审计禁止从像素估读数值 | run `104`（把 Tue 288 读成 290） |
| 抽取把"数据点须用圆形标记"明确归入 `wrong_chart` | run `023` 的错分类 |

## 5. 两个机制性发现

### 5.1 判定的双峰抖动

**同一个 prompt、同一张图，模型会在 `NONE` 和一份长缺陷清单之间翻转。**

| run | 重复调用结果 |
| --- | --- |
| `038` | `NONE`，`NONE`，9 条缺陷 |
| `046` | 20 条，`NONE`（收紧措辞下）；16/16/16（原始措辞下） |
| `030` | 独立调用 3 次都报 20/20/22 条，而真实 `validate()` 那一次报 0 |

36 组配对里布尔结论翻转 4 次（约 11%），且受影响的 run 呈**双峰**而非程度上的抖动。

**解析器不是原因**：`_DEFECT_RE` 已验证能解析样本中的每一份回复，包括计数翻转的那些 run。抖动在模型侧。

由此得出的方法论约束：

- **单个 run 的 MCC 差异低于约 0.1 不构成证据。**
- 判断改进要看**错误类型是否消失**（如"存在性规则让 `wrong_chart` 的 FN 从 5 降到 4"），而不是 MCC 的小数位。
- 报告任何 MCC 增量前，应重跑一次子集以取得噪声带。

这也直接指向 Part 4 的改进方向：**对可读性这一路多次调用取多数**。它是整个验证器里最便宜的一次调用（仅图片、无指令、无代码、约 400 输出 token）。

### 5.2 两个方向的默认偏置是相反的

| | 默认倾向 | 观测 |
| --- | --- | --- |
| 审计（数据/图表） | 倾向于答 OK（漏报） | 4.4：要求"存在"的条目全部被判 OK |
| 可读性 | 倾向于报缺陷（过报） | 4.6：常规轴标签被判"太小" |

这意味着两路需要**不同方向**的提示词约束，不能用同一种"更严格/更宽松"的思路统一处理。

## 6. 当前结论

- 同一子集上 macro-MCC：**0.0415（基线，全量）→ 0.5134（迭代 3，32 run 子集）**；同子集的基线为 0.0214。
- **结构性确立**的三点：`execution_failure` 可由产物确定性判定（满分）；`hard_to_read` 由"找缺陷"式提问可从 0 召回转为有效召回；拆解式审计把 `wrong_chart` 从 0 提及提到 `TP=8`。
- **仍在噪声范围内**的：`wrong_data` 的 ±0.02 量级波动、以及任何单轮 micro 变化。
- **未验证**：迭代 4 的三处定向修复。

## 7. 未决问题（Part 4 候选）

1. **多数投票**：对可读性多次调用取多数，用于对抗 5.1 的双峰抖动。成本 ×3，仅作用于最便宜的那一次调用。
2. **`wrong_chart` 剩余 4 个假阴性**：`016` `028` 的"缺图例"、`021` 的"缺 xlabel" 在存在性规则下仍未被抓住，说明规则需要在**输出格式**上强制（例如要求逐字引用找到的标签文字，找不到则字段为空即判违规）。
3. **`wrong_data` 剩余的 4 个假阳性 / 4 个假阴性**：`029` 的"三种分布类型"被误归为 chart。
4. **是否给 chart 审计也送代码**：数据审计已论证必要，chart 审计（轴类型、图例、配色）以看图为准，送代码可能诱导模型跳过读图。这是一个可直接 A/B 的开关。
